# 门店账号新增与登录检查 · 2026-09-06

检查源码：`10cd3b8891387cae9422d2edc8a99965ed7bed86`。本次是问题排查与证据交接，未修改业务实现，也未执行生产数据写入、SQL、云函数或小程序发布。

正常新建门店、生成 Auth 账号、建立员工与门店绑定、用初始密码登录同一门店的隔离流程通过；错误密码会被拒绝。确认的问题主要集中在恢复旧账号、写入结果确认和失败反馈，不能将其表述为每次新增门店都会失败。

## 按影响排序的发现

### 1. 恢复已有账号时，本次初始密码未生效却没有提示（P1）

服务端发现已有同手机号 Auth 账号时保留原密码，返回 `authAccount: recovered`、`passwordInitialized: false`。这本身是保护已有凭据的正确行为；小程序却只读取门店编号并直接跳转，完全忽略密码是否初始化。操作人可能把本次填写的密码交给门店，然后遇到密码错误。

- 位置：[服务端返回结果](../../cloudfunctions/staffAccount/index.js#L4805)、[小程序创建成功处理](../../miniprogram-app/miniprogram/pages/store-create/index.js#L42)。网页版 `store-create.js` 也只读取门店编号，存在同类反馈遗漏；本轮只做静态对照，未做网页版完整交互验收。
- 隔离证据：旧 Auth 密码与本次输入不同；服务端返回恢复成功且不改密码；实际小程序控制器立即跳转，没有保留原密码的说明。
- 修复方向：明确区分“新账号”和“恢复已有账号”，展示服务端密码状态；恢复时提示使用原密码或正常改密流程，不能为了让本次输入生效而自动覆盖旧密码。

### 2. 数据已经保存，但空返回结果被当成失败（P1）

门店资料写入后仅依赖 `RETURNING` 返回编号；账号绑定门店同样只检查是否有返回行。代码缺少对已提交结果的精确回读确认。仓库其他员工写入路径已有空返回后的回读处理，门店这两处尚未覆盖。

- 位置：[门店写入后检查](../../cloudfunctions/staffAccount/index.js#L2012)、[绑定结果检查](../../cloudfunctions/staffAccount/index.js#L1736)。
- 隔离证据：模拟数据库已提交但返回空数组，建档阶段返回 `DATABASE_ERROR`，账号尚未继续建立；绑定阶段在绑定已存在时仍返回 `STORE_BINDING_FAILED`。`stores.store_account_id` 与 `staff_store_assignments` 两种代码路径均出现后者。
- 修复方向：使用可信的本次操作标识、UID 和门店标识进行有界回读，确认后才返回成功或安排恢复；不能只按同名门店猜测归属。需要共享 `staffAccount` 修改及独立版本部署。
- 边界：本次注入的是受控空返回故障，没有证明当前线上门店新增已实际遇到这种返回，也没有对两个数据库布局做真实数据库执行验收。

### 3. 超时、成功后跳转失败，均可再次发起创建（P2）

小程序只用 `submitting` 防止请求进行中重复点击，在 `finally` 无条件解除。调用超时的 `submissionUncertain` 没有被处理，用户只看到普通错误；成功后 `redirectTo` 没有失败回调，也没有保存已确认成功的页面状态。留在原页后再次点击会重新调用创建接口。

- 位置：[提交与收尾](../../miniprogram-app/miniprogram/pages/store-create/index.js#L28)、[导航调用](../../miniprogram-app/miniprogram/pages/store-create/index.js#L47)。
- 隔离证据：模拟调用超时后再次点击，服务调用计数为 2；模拟成功后的跳转失败，再次点击同样发起第 2 次调用。
- 修复方向：区分已确认成功、已确认失败和结果未知；成功后保留门店编号并提供重新进入页面，未知结果先核对门店目录／原操作结果，避免把再次创建当作恢复查询。
- 边界：确认的是重复请求和反馈缺失。服务端已有按手机号恢复与绑定检查，本次没有证明会生成两个可登录账号，也未进行并发生产写入。

### 4. 本地缓存清理失败，会把创建成功显示成错误（P2）

服务端已成功后，删除本地待恢复缓存仍位于同一 `try` 中。`wx.removeStorageSync` 抛错会进入创建失败分支，阻断跳转并重新允许提交。异常阶段保存待恢复缓存抛错，也可能覆盖原本更有价值的服务端错误。

- 位置：[成功后缓存清理](../../miniprogram-app/miniprogram/pages/store-create/index.js#L46)、[失败后缓存保存](../../miniprogram-app/miniprogram/pages/store-create/index.js#L49)。
- 隔离证据：注入缓存删除失败，服务端成功返回后页面 `error=true`，未跳转；后一个缓存保存场景本次仅静态确认。
- 修复方向：已确认的服务端业务结果与本地缓存维护分别处理；缓存故障必须可见，但不能反转创建结果或诱导重新创建。

## 其他确认的缺口

- 服务端返回密码审计写入告警时，小程序忽略 `warning` 直接跳转；账号仍可能可用，但总部看不到需要补查审计的提示。隔离告警响应已验证。
- 门店资料写入后、联系人写入失败，会在 `createOrRecoverStore` 内提前抛错，尚未进入外层账号阶段的补偿处理；留下未完成门店资料。隔离故障已验证，不代表永久无法恢复：既有按电话／资料恢复能力仍然存在。应明确传回待恢复标识与结果状态，不应随意删除可能已被其他流程绑定的门店。

## 方法、结果与限制

使用真实 `staffAccount` 分派函数、`createOrRecoverStore`、`createStaffDatabaseProfile`、小程序创建页控制器和 `session.js`；Auth、SQL、人员回读、微信缓存及导航均为隔离替身。正常流程串接同一创建结果和登录身份，异常检查针对返回为空、旧凭据、超时、导航及缓存失败。未访问真实新门店密码、未新建或改变生产账号。
