# PDF 上传第二轮：分块、原生 COS 表单与备用域名

日期：2026-10-16，悉尼时间（AEDT）。本轮测试开始于 18:06，实传结束于 18:20；超时请求的迟到写入最终核验另见下节。

用户在前轮提出“追加最多 10 MB、不发布资料、先备份、仅清理测试文件”的明确范围后回复“继续测试”，随后要求不要局限一种方法、先学习其他实现。本轮仅测试既有项目文件存储，不修改业务代码、账号、权限、桶配置、云函数、小程序或静态网站，不建立收费资源、不使用加速域名。

## 从官方资料得到并实际应用的区别

- [小程序直传实践](https://cloud.tencent.com/document/product/436/34929) 明确区分 `wx.request` 的二进制 PUT 与 `wx.uploadFile` 的 COS POST 表单。后者是另一种协议与原生文件发送入口，不是把现有 PG 签名 PUT 地址换成 POST；此次直接对原生 COS 的独立测试键签发精确 policy。
- [分块上传](https://cloud.tencent.com/document/product/436/14112) 允许分别上传并组合文件块。本轮使用四块各 1 MiB、单路串行、每块 MD5 校验，以及完成后的整文件下载 SHA-256 校验；没有以开始合并时的 HTTP 200 代替完整成功证明。
- [官方 Node SDK 源码](https://github.com/tencentyun/cos-nodejs-sdk-v5/blob/master/sdk/base.js) 包含普通 COS 域名到 `tencentcos.cn` 备用域名的切换机制。本轮重新针对该 host 签名，不复用主域名签名，不改 DNS/IP、不借用代理，HTTPS 与证书校验保持开启。只读确认备用域名仍访问同一项目同一区域的既有桶，随后比较同一份第一数据块。
- [官方外网上传缓慢排查](https://cloud.tencent.com/document/product/436/53932) 将网络、运营商、跨境和额外中转列为排查方向；这只是下一步对照依据，不足以据此把用户手机故障归因到某一网络。本轮没有启动该文档示例的额外 20 MB 自动探针，也没有擅自开启收费全球加速。

## 测试条件与计时边界

测点仍是 **Mac / curl，不是物理微信手机**。测试使用与前轮完全相同的 4,194,304 字节纯合成 PDF，以及前轮 291,840 字节小样本。文件没有个人资料，不调用业务发布、资料确认或读取已发布业务内容的接口。

官方工具返回的旧临时凭据过期后，脚本在任何上传前明确停止；通过官方 CLI 刷新了属于同一环境的临时凭据才继续。永久密钥、service-role Key、policy、签名、文件键及原始回执均未提交公开仓库或下发产品客户端。

所有实传串行、没有自动文件重传。每次创建分块任务、发送文件块、完成组合、表单上传、删除对象与舍弃分块前都通过新鲜完整备份门禁。备份时间是运维实验的安全开销，不作为产品传输速度；表中“传输”包含该请求发送和等待回执，不能冒充纯服务器计算时间。

本轮实际协商到并取得响应的请求均为 HTTP/1.1；没有取得响应的请求按未知记录，不能据请求配置宣称已使用 HTTP/2。

## 实测结果

| 方法 | 样本 | 上传 / 回执等待 | 结果与完整性 |
| --- | --- | ---: | --- |
| 原生 COS 串行分块 | 4 MiB，四块各 1 MiB | 四块合计 **236.489 秒** | 四块均 HTTP 200，MD5 一致；组合完成后完整下载 SHA-256 与原样本一致 |
| COS POST policy 小样本预检 | 285 KiB | **11.942 秒** | HTTP 201；完整下载 2.796 秒、SHA-256 一致；签名、policy 与接口可用，但不代表大文件提速 |
| COS POST policy 整文件 | 同一份 4 MiB | **180.004 秒** | curl 退出码 28、无 HTTP 回执；结束后 HEAD 404，未发现完整对象 |
| 官方备用域名分块对照 | 与第一种方式完全相同的第一块 1 MiB | **68.835 秒** | HTTP 200，ETag / MD5 与主域名第一块一致；没有更快，不把单块结果冒充完整 4 MiB 文件测速 |

分块四次分别为 **53.838、85.421、59.714、37.516 秒**；初始化 1.363 秒、完成组合 1.742 秒。实验从初始化请求开始至组合确认共约 314.625 秒，包含逐次备份及核验，不能把它与只有传输时间的 236.489 秒混用。完整 4 MiB 对象独立下载耗时 **4.247 秒**，实际长度及 SHA-256 均正确。

4 MiB 表单请求在超时前，curl 记录已发送 **1,965,826 字节**，该数字含表单封装，并非 COS 已存储的 PDF 字节数；没有响应首字节。其 DNS 0.002 秒、TCP 连接 0.332 秒、TLS 完成约 0.673 秒，不能把 180 秒全归因于 DNS 或连接建立。小样本表单传输了 295,494 字节，其中 PDF 为 291,840 字节。

备用域名与主域名通过正常 DNS 解析得到的地址集合不同，且备用域名对该项目桶的只读请求成功；这不证明整个网络路径独立或稳定更优。此次相同第一块在主域名为 53.838 秒、备用域名为 68.835 秒，只有单次对照，没有统计显著性或“换域名一定更快”的结论。

## 与照片实际上传链路的区别

照片必须按入口区分，不能笼统说“照片与 PDF 都是同一路径”，也不能以本地预览解释用户反映的实际上传成功更快。

- **打卡照片、核销现场人脸照片**：考勤客户端 `pages/attendance/index.js` 将 `imageBase64` 交给 `callFace("clockInTeacherAttendance", ...)`；`services/api.js` 通过云函数调用发送。`cloudfunctions/faceRecognition/index.js` 完成人脸校验后，由 `uploadVerificationPhotoObject` 使用服务端 `manager().storage.uploadObject` 保存。考勤还会完整读取保存结果并比较长度和 SHA-256，确认后才返回打卡结果。因此这个入口确实不是手机直接向 PG 签名 PUT 地址发送照片，用户反映“实际上传也快”不能被当成只是预览。核销现场人脸入口 `verifyCustomerFace` 同样先接收照片，再经 `persistVerifiedFaceEvidence` 保存。
- **工单补充照片**：当前 `pages/order-detail/index.js` 先把本地文件放进照片位，标为 `pending/PREPARING`，再后台上传与服务端确认。其常规上传使用 PG 网关签名 PUT，不能与上述现场人脸入口混为一谈。本地立即显示只能解释“出现得快”，不能证明或否定服务端保存得快，也不能推断它在用户当次运行时一定走了常规通道而非受控兼容通道。
- **培训 PDF**：`services/training-material-upload-queue.js` 先申请签名，手机向存储入口 PUT 文件字节，再调用确认接口验证 PDF 前缀、长度和幂等发布。本轮尚未对“同手机、同网络、同体积，云函数接收再保存”做对照，不能宣称照片通道已经证明适合 PDF 或必然更快；更未因此擅自修改既有 PDF 全直传契约。

现场人脸链路与 PDF 的首段入口、发送封装和服务器后续操作不同，这是已经核实的代码事实；其中哪一段解释实际速度差，仍是待测假设。没有采集用户当次照片的实际字节数、通道及分阶段时间，不能笼统归因于照片压缩，尤其不能声称所有照片都会先缩小。

本轮直接测试存储协议，没有学习资料发布或列表刷新，仍复现大文件慢传。现有证据不足以把问题简单归为 PDF 解析、列表刷新、按钮、上传 API 名称或手机本身；也不能把本机 curl 结果当作微信原生 `wx.uploadFile` 的实测性能或可直接部署的客户端方案。

## 当前结论与下一步

目前三种新对照均没有满足上传秒级目标。分块提升了本次 4 MiB 的完整传输可验证性，但速度不合格；原生 COS 表单和备用域名都不能据此作为已验证的提速修复上线。

下一步应优先对用户反映实际更快的照片入口做可比验证，而不是继续盲换 PUT/POST：先确认究竟是现场人脸还是补充照片，记录文件实际字节数和服务端保存完成时间；再在实际手机上控制同网络、同体积并分开统计准备、签名、实际传输、确认发布。现有照片业务接口只接受对应人脸/JPEG，不能把 PDF 伪装成照片调用，也不能制造测试打卡或工单；如要新增隔离的 PDF 云函数接收实验，应明确其部署和安全范围，不能直接改变现有全直传契约。若在境外访问国内存储，仍需实测确认线路影响；加速或新增服务涉及费用和部署，应另行决定。不能无界重复整文件上传，也不能通过缩短超时、伪造成功或放宽私有权限掩盖未达标结果。
