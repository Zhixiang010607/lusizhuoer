# 点击登录等待优化 · 2026-09-07

用户反馈的是点击“登录”后，进入主页之前等待较久。本次只修改微信小程序的共同登录链路，没有修改网页、云函数或数据库。

## 已确认的重复等待

原流程在认证成功、`refreshSession()` 和 `getAccessToken()` 完成后，再调用 `getCurrentUser(true)`。当前固定依赖 `@cloudbase/js-sdk@3.7.1` 中，`true` 会调用 `LoginState.user.refresh()`，后者通过 Auth API 再获取一次用户资料；这一步位于服务端业务身份回读之前，会增加一轮串行网络等待。

现改为 `getCurrentUser(false)`，先读取官方 SDK 刚同步的当前身份；读不到时仍调用既有 `getUserInfo()` 重新获取资料。这里读取的是 SDK 身份，不是本地业务权限缓存。仍然依次执行：退出旧 SDK 会话、重新认证、确认完整 UID、刷新会话、核对 SDK 当前 UID、通过服务端 `staffAccount.session` 确认账号状态、角色和门店／老师绑定。两种登录共用此流程；只有原定的短暂身份同步错误可以有限重试，且不重复认证或兑换微信一次性 code。

首页数据请求由主页进入后发起，本次未把权限确认延后到进入主页之后，也未加入提前显示登录成功的逻辑。

## 验证

- `node --check miniprogram-app/miniprogram/services/session.js` 通过。
- `node --test tests/*.test.js`：324 项通过，0 失败。
- 回归包含密码与微信登录、老师新建后登录、令牌同步重试、错误密码、缺失 UID、SDK 身份不一致、封存账号、缺失 SDK 用户的资料获取兜底，以及兜底返回其他 UID 时在业务请求前拒绝并清除会话。
- 额外调用实际安装 SDK 的 `Auth.prototype.getCurrentUser`，使用隔离的内存 LoginState 验证方法行为：原参数 `true` 触发 1 次强制资料刷新，新参数 `false` 触发 0 次，且仍执行本地身份信息完整性检查。没有使用真实账号、密码或线上业务请求。

这证明正常链路减少了一次重复资料读取，不能据此声称真实手机提速若干秒或保证所有慢登录都已解决。实际等待仍取决于认证接口、身份服务和用户网络；真机耗时需使用新预览复核。
