# 小程序培训 PDF 全直传与慢回执恢复

## 决定与范围

- 用户明确要求所有培训 PDF 直传、尽量减少等待。小文件也不使用云函数携带文件字节；保留私有签名 PUT、100 MiB 上限、总部上传和老师阅读权限。
- 仅改小程序培训上传队列和恢复阶段文字。Web、云函数、数据库、核销、BLE、人脸、扣次及工单照片实现未改；用户已有 `project.config.json` 与未跟踪图片不提交。
- 签名申请和发布确认仍为元数据请求；PDF 完整字节只发给签名存储地址，不加 Base64、中转或重复文件读取。

## 实现

- 正常成功链路仍是一次申请地址、一次二进制 PUT、一次发布确认。PUT 开启 HTTP/2 协商，响应按纯文本处理，不解析无用 JSON。
- 保留原 180 秒传输硬上限，不强行中断仍在传输的慢网请求。初拟按文件大小缩短至 20 秒的方案已撤销，避免把慢网的正常上传变成超时重传；提速来自传输协商和已完成对象的回执恢复，而不是更快报错。
- 最多 1 MiB 的文件若原 PUT 8 秒未返回，仅核对一次原请求。服务端已经完成内容验证和幂等发布，才结束原回执等待；文件仍未上传完则继续同一个 PUT，不中断、不并发重传、不循环探测。更大文件不触发早期探测。
- 核对期间显示“核对上传结果”，不冒充仍在传字节；只有 2xx 完整传输回执或服务端权威发布结果才更新实际已传字节，不伪造百分比。
- 每次不确定的 PUT（包括最终尝试及 409 冲突）都先用原请求恢复结果。8 秒时的未完成结果不能作为稍后重传依据，必须在原 PUT 结束／失败后重新确认；仅最新确认仍未完成时，才使用相同签名、相同完整字节串行重试。移除多余 350ms 固定等待。
- 权限／格式拒绝仍终止；结果暂不可读取则保留原引用，不能当“未上传”重传。检测到换账号时停止原传输，保留可恢复任务、不安排旧账号重试。
- 超过 5 秒或失败的原生传输在本地控制台只记录文件字节数、耗时、HTTP 状态及可用的 DNS／连接／TLS／响应前等待时长。只白名单取数字，不记录 URL、签名、请求头、文件名、UID 或原始 profile，不增加遥测请求；用于后续真机定位实际瓶颈，不能把 `untilResponseMs` 当成纯服务器处理耗时。

## 验证与限制

- 完整仓库 562 项测试全部通过，三个修改／测试 JavaScript 的语法检查与 `git diff --check` 通过；专项包括正常小文件、已完成但丢回执、早期未完成不重传、确认和回执同时返回、早期缺失后实际完成、最终尝试恢复、409、403、暂时读取故障、早期读取失败不能掩盖终止性 HTTP 拒绝、换账号、大文件单 PUT、诊断信息去敏和缓存／离页队列等情况。
- 独立只读复核指出“早期 missing 已过时”会导致重复 PUT；已修正，并加入首轮及最终轮两项运行测试。此处的模拟 8 秒只证明控制流，不是真机速度样本。
- 微信原生隔离检查：手机 320／390／430px、iPad 768／834／1024px 竖屏及 1024×768 横屏；合成恢复／失败状态下 12 个主要容器、说明与操作的横向越界均为 0。状态、重试与移除文字可见，布局、按钮和字号未改。
- 原生检查只在内存使用合成身份及展示数据；阻止网络请求，不点击上传、删除或业务提交。最后恢复原 iPad 横屏配置，重启逻辑层后确认回到公开公司启动页、合成状态与网络拦截均消失；无持久测试绕过。
- 原生截图生成物：`output/pdf-direct-20261016/phone-430.png`、`output/pdf-direct-20261016/tablet-1024.png`，不提交 Git。
- 真实手机 PUT 的 DNS／连接／实际发送／存储回执耗时尚未捕获，不能把一笔约 430ms 的发布确认日志等同于上传全程；也不能宣称本轮已实测达到秒级。

API 参数依据微信官方 [RequestOption 类型定义](https://github.com/wechat-miniprogram/api-typings/blob/master/types/wx/lib.wx.api.d.ts)：二进制请求、HTTP/2、超时与 RequestTask.abort。没有把 POST multipart 的 `wx.uploadFile` 错接到现有 PUT 存储协议。
