# 门店业务与总部数据系统

当前前端版本：`0.15.0`

## 腾讯云客户人脸识别后端

`cloudfunctions/faceRecognition/` 是 CloudBase 人脸与业务云函数源码。它使用腾讯云人脸识别的人员库与 1:1 核验能力，人员库 ID 为 `lusizhuoerdatabase`；客户首次授权建档时录入人脸，后续核销只与已经选定客户的档案核验。`cloudfunctions/verificationPhoto/` 是独立核销照片云函数，不安装腾讯人脸 SDK，只处理照片查看、导出和三个补充照片位的上传／取消／恢复。函数密钥只能配置在 CloudBase 环境变量 `FACE_SECRET_ID`、`FACE_SECRET_KEY` 中，严禁出现在网页代码、GitHub 或文档中；照片函数不需要这两个变量。

前端通过已登录 CloudBase UID 调用云函数，门店、总部及客户范围均在服务端重新校验。正式处理真实人脸数据前仍必须确认活体检测服务、客户明确授权、人脸数据删除渠道和访问审计均已启用。

## 员工登录与账号唯一性

- 一个中国大陆手机号只能绑定一个业务身份；手机号码全局唯一，已绑定后不可再次注册或改绑给其他总部、运营、门店或老师身份。
- 账号创建仅由已授权总部在网页端发起；后端同时创建身份认证用户与业务档案绑定记录。未预先绑定的手机号不能通过短信自助注册进入系统。
- 员工可使用“手机号 + 密码”或“手机号 + 短信验证码”登录；两种方式对应同一身份和同一权限，不产生第二个账号。
- 修改密码须由当前已登录用户完成短信二次验证；总部可发起重置，系统记录操作人、时间和原因。初始 12 位密码仅作首次/应急登录凭据。

## 总部基础资料创建规则

- 门店创建为独立页面；填写门店名称、完整地址，并可添加多组联系人姓名与电话。提交后自动生成门店编号、门店账号与12位数字初始密码。
- 老师和运营人员创建必须填写姓名、身份证号码和联系电话；系统自动生成编号，身份证号码在老师和运营人员的完整人员库中不可重复。同名时显示名称自动追加 `+1`、`+2` 等顺序号。
- 老师管理和运营管理支持按姓名或身份证号码查询；按姓名查询时，结果同步显示身份证号码以确保唯一定位。两个页面只支持封存，不提供删除操作。
- 总部侧栏不再设置“创建”菜单；门店、产品、老师与运营人员均只能从各自管理页的“新增”按钮进入创建页。
- 门店管理首次进入仅提供“门店名称＋省/州＋城市＋区”选择和新增门店；确认选择前不显示门店资料。确认后展示门店信息、统计和“查看门店页面”入口；同名门店自动以 `1`、`2`、`3` 区分。
- 示例门店统一使用中国省、市、区；新建门店时省、市、区为联动下拉选择。完整三级行政区划数据保存在本地 `china-regions.js`，离线打开原型时同样可用。
- 门店管理还支持手动输入门店名称并依次选择省、市、区；系统先弹出详细地址和联系人方式供核对，确认无误后才跳转至门店页面。
- 产品管理一次展示全部产品；点击某个产品后才显示其资料、门店统计和独立产品页面入口。
- 核销办理和补录核销均使用人脸识别核验，不再要求拍照；只有活体检测与人脸比对通过后才能提交核销，正常核销才会发送设备开启信号。
- 充值不需要人脸识别，也不采集刷脸或拍照凭证；确认客户、项目和充值次数后即可提交审核。
- 门店账号和运营账号密码仅总部可在对应管理页面查看或修改；静态原型中密码仅保存在当前浏览器会话，正式部署须改由后端保存密码哈希并记录审计日志。

直接双击 `login.html` 或运行 `open-dashboard.cmd` 即可离线打开统一登录入口，不需要安装依赖或启动服务器。
登录页按“总部、运营、门店”的顺序显示三个身份选项；门店登录必须选择所属门店。静态版接受任意非空密码，
只在当前标签页的会话存储中保存单一演示会话，不保存密码；重新选择身份登录时先清除上一身份会话，避免角色状态混用。
总部进入数据库全局工作区；运营只进入显示本人数据库资料的全局视图，并只保留充值审核与核销审核；门店直接进入所选门店工作区。未登录访问业务页面、直接输入其他身份页面地址、
或者门店修改URL中的门店编号时，`auth-ui.js` 都会拦截并返回本身份首页。侧栏只生成当前身份允许的入口，并提供账号、门店及退出登录。
总部的客户、充值和核销查询使用同一套数据库页面，可查看全部门店或选择一个具体门店；门店账号的三类查询固定锁定到登录门店，不能选择“全部门店”或其他门店。页面选项只决定筛选条件，最终权限仍由云函数根据 CloudBase UID 校验。
前端路由隔离不是安全边界：`staffAccount`、`faceRecognition` 和 PostgreSQL RLS 都会再次按 CloudBase UID、账号状态和角色校验。运营账号不能调用客户查询、门店、产品、管理或总部统计接口；只能从真实审核记录进入受工单上下文约束的客户与业务只读详情。

总部与门店共用同一套“业务办理”页面和主体流程。总部侧栏提供完整的四个入口；进入任一页面后，必须先在页面顶部明确选择并确认一个 `ACTIVE` 门店，才能读取客户、项目、老师或提交业务。总部办理选择器不提供“全部门店”，也不接受缺失、停用或伪造的门店 ID；切换门店会清空当前客户确认、人脸结果、表单和幂等请求状态。门店账号仍由服务端 UID 锁定到登录门店，不显示可切换门店选择器。

- `customer-create.html`：客户建立，必填姓名、生日，强制现场拍摄建档照片，保留面容录入、活体/质量检查与授权逻辑，并填写特别注意事项；
- `recharge-create.html`：办卡充值，可选择现有客户并自动带出只读生日，或手动输入姓名和生日；只匹配已确认门店的活跃客户，确认后选择项目和次数，充值不做人脸识别；
- `verification-create.html`：核销办理，沿用已确认门店的活跃客户检索，选择项目和老师，人脸核验及现场照片绑定成功后才允许正常核销并发送设备开启信号；
- `verification-supplemental.html`：补录核销，复用相同客户确认、项目余额、人脸核验与照片绑定流程，必须填写补录原因，提交后进入审核且不发送设备开启信号。

总部、门店的四个入口复用相同 DOM、校验、提交和返回链，只在顶部门店上下文与侧栏身份文案上有差异。总部办理的门店选择只影响当前业务页面，不改变总部查询页仍可使用的“全部门店”筛选；每个云函数请求都会再次按当前 UID、角色和目标门店状态校验，不能依赖前端缓存扩大范围。

办卡充值和核销办理的客户区提供两种检索模式：“现有客户下拉框＋生日”以及“手动输入姓名＋生日”。现有客户模式选择带编号的客户后，生日由客户主档自动带出并保持只读，不能在查找流程中修改；只有手动模式允许选择生日。查询后左半栏显示
客户建档时拍摄的当前有效照片、姓名、生日和客户编号，不再显示各项目剩余次数；必须点击“确认此客户”后右半栏才解锁。建档照片不存在或读取失败时不得确认客户。办理页只预载前 100 位活跃客户，其他客户按姓名＋生日走服务端精确查询；照片短时地址在授权后复用。核销人脸原图优先保留到最长边 1920 px、JPEG 0.92，并另存 480 px 缩略图；只有超过 3 MB 才逐级缩小。
切换方式或修改条件会撤销确认并重新锁定。
核销项目下拉框只加载剩余次数大于零的项目，并直接显示剩余次数。

静态原型只保存当前标签页中的演示状态，不采集真实面容或照片。正式部署时，客户和门店范围必须由服务端会话确定，
面容录入必须使用受控摄像头、活体检测、质量检查、加密模板和授权审计，不能由前端自行声明成功。
客户建立、办卡充值和核销办理页面在桌面端使用尽量占满可用工作区的拉伸布局；充值和核销采用左右双栏，
左侧持续显示客户检索结果，右侧完整显示项目、次数、采集状态和提交结果，窄屏时自动切换为单栏。

项目栏中的“管理”可以展开三个子页面：

- `store-management.html`：新增、选择、查看和删除/停用门店；查看老师核销表、项目核销表和本门店全部客户项目次数；
- `project-management.html`：新增、选择、查看和删除/停用项目；查看项目在各门店的充值与核销统计；
- `teacher-management.html`：新增、选择、查看和删除/停用老师；查看老师在各门店、各项目的核销统计。

每个门店都有独立的 `store-detail.html` 页面。门店管理页提供“查看门店页面”按钮；项目统计、老师页面、
充值/核销查询和业务详情中的门店可以点击进入对应门店页面。总部从门店管理进入时以真实数据库门店 ID 读取所选门店，门店账号进入时由服务端 UID 锁定自身门店；基础资料、项目统计、老师统计和分页客户均来自同一门店看板数据库接口。

每个项目都有独立的 `project-detail.html` 页面。项目管理页提供“查看项目页面”按钮；门店页面、老师页面、客户档案、
充值/核销查询和业务详情中的项目可以点击进入对应项目页面。项目页面显示基础资料、设备权限代码、门店老师统计、客户权益和档案审计。

门店客户表中的每个客户编号均可点击并进入 `customer-detail.html`。客户详情页当前按常规后台档案设计，显示基础资料、
全部项目权益、充值记录、核销记录、异常修改/删除审核、照片权限说明和档案审计；不同项目不覆盖，旧版本和原始记录继续保留。

每个老师都有独立的 `teacher-detail.html` 页面。老师管理页提供“查看老师页面”按钮；门店老师核销表、核销查询、
客户核销记录和核销详情中的老师编号均可点击进入对应老师页面。老师页面显示基础资料、关联门店与项目、
核销统计、最近核销明细、照片/资格附件权限说明和档案审计。
客户详情页使用URL客户编号参数定位对象，后续部署时由后端按登录权限读取对应真实档案。

门店项目栏新增“业务管理”折叠菜单，其中“客户管理”锁定到登录门店。客户可以按照“全部客户、有信息但没有充值、已充值但没有消费、已充值并已有消费”四档业务阶段，
以及“全部、活跃、已存档”三档客户状态组合查询。

项目栏新增“查询”折叠菜单：

- `customer-query.html`：数据库客户查询，业务阶段统一为“有信息但没有充值、已充值但没有消费、已充值并已有消费”三类；总部可选全部或指定门店，门店锁定本店，并支持活跃、已存档和恢复；
- `recharge-query.html`：数据库充值查询，总部可选全部或指定门店，门店锁定本店，分别显示原单状态与作废申请状态；
- `verification-query.html`：数据库核销查询，总部可选全部或指定门店，门店锁定本店，显示核销类型、审核状态和人脸核验记录；核销不提供作废状态或作废入口。

门店账号无权删除任何客户，也无权修改姓名、生日或其他客户资料。客户编号、姓名、生日、所属门店、照片、人脸信息、项目权益、次数和审计字段在门店客户端全部只读。
门店唯一允许的客户管理操作是把活跃客户设为存档，或把已存档客户恢复为活跃；每次状态变更均记录账号、门店、原状态、新状态和时间。
存档不会删除充值、核销、版本、照片或审计记录，已存档客户可以重新查询并恢复。
办理充值或核销时使用“客户姓名＋生日”组合查找，门店条件由登录会话锁定，并且只返回活跃客户；
同名同生日客户通过客户编号区分。办理页面的活跃客户检索与充值、核销历史查询相互独立；历史查询另行提供现有客户精确选择和手动姓名匹配两种模式。

项目栏新增“审核”折叠菜单：

- `recharge-review.html`：审核新充值，以及充值修改和删除申请；
- `verification-review.html`：只审核补录核销；正常和体验核销不进入审核队列，核销作废流程已停用。

两个审核页按门店、申请类型和审核状态筛选，支持通过、驳回和必填审核备注。
审核记录显示发起门店、账号和人员姓名。总部与运营均可点击工单号进入业务详情，也可点击客户进入客户主页；运营的详情入口只作为审核下级页面，不生成查询或管理菜单。运营客户主页必须携带真实审核工单上下文，服务端校验工单与客户归属后只读返回资料、余额和业务历史，不返回照片、不显示封存／激活操作。审核结果写入数据库并由余额状态机统一生效。
门店只可在已通过的正常充值工单详情页提交一次作废申请，必须填写原因并二次确认。核销工单一经提交不提供作废或撤销入口；误核销必须另行提交充值工单补回次数，避免反向修改核销记录。核销详情右侧固定显示“门店留言”和“总部留言”，长留言可在各自区域内上下滚动，不再保留底部重复留言区。
充值与核销详情页均可导出单笔完整工单 PDF 或高清图片，文件名固定为“客户姓名+项目+充值／核销”。导出页头完整包含工单类型、单号说明、当前审核状态及状态说明。核销导出按当前详情权限读取五个照片位的高清原图并写入下载文件；刚提交且仍在当前页的照片优先复用本地 Blob，服务端兜底通过鉴权存储通道直接读取私有对象，不依赖临时下载地址。数据库明确为空的照片位会保留占位，数据库已有的照片则必须全部下载并解码成功，否则取消本次文件生成并提示重试，绝不以占位静默替代。签名地址和照片原图不写入浏览器持久存储，同一页面连续导出 PDF／JPG 时仅在内存中复用已经授权读取的照片 Blob。
`auth-ui.js` 按总部、运营、门店和老师路由白名单隐藏无权菜单并阻止直接串页；运营菜单只有本人首页和两个审核页，白名单另保留由审核链接进入的客户、充值与核销只读详情页；门店不能进入审核、管理或其他门店详情。
总部、运营和门店的会话、首页、侧栏与数据范围分别处理，后端接口仍会再次校验权限。

充值查询和核销查询都提供门店、客户和项目名称条件，并在结果中始终显示项目名称；不使用生日作为历史记录查询条件。
客户条件可在“选择现有客户”和“手动输入姓名”之间切换：下拉选择按客户编号精确查询；手动姓名匹配会在候选提示和结果中显示全部同名客户，并通过客户编号和所属门店区分。客户编号可以进入客户详情。
同名客户在结果和详情中的显示名称必须追加顺序号，例如“张静1、张静2、张静3、张静4”，
使每个不同客户编号在视觉上也能直接区分；手动输入原姓名“张静”会一次返回全部同名客户。
充值编号进入独立的 `recharge-detail.html`，核销编号进入独立的 `verification-detail.html`；
两个详情页分别显示完整业务字段、原始记录和上一版本、异常审核及操作审计，核销详情另显示现场照片权限和设备信号结果。
充值详情页“版本与原始记录”表中的每个版本编号都可以点击；点击后在同一充值详情页加载该版本，并标记“正在查看”，
其他历史版本和当前有效版本继续同时保留在版本表中。
核销详情页采用相同规则：V1、V2及以后所有核销版本编号均为链接，点击后加载对应核销版本并保留原照片证据关联。

所有充值和核销（消耗）信息必须绑定并显示门店。查询结果、客户档案、记录详情、异常审核及每一个历史版本都保留门店编号和名称；
正式系统创建记录时门店字段不可为空，并保存发生时的门店名称快照。

每一条新核销记录必须固化客户建档原始留存照引用，并保存一张不可修改的本次人脸核验现场照片。照片未拍摄、上传失败、保存失败或数据库绑定失败时，核销不得成功、不得扣减次数，
也不得向物理机器发送开放权限信号。每张核销单另有 3 个补充照片位；仅真实提交账号可在服务器记录的 `submitted_at + 24 hours` 之前上传或替换，审核进行中也不冻结照片，超过截止时间后所有角色只读。总部账号只有在自己就是该工单原提交账号时才具备这项 24 小时写权限；其他总部、门店、老师或运营账号不能代为上传或替换。核销详情固定显示 5 个照片位，首屏只懒加载私有缩略图，点击单张照片时才签发并加载高清原图。补充照片的“拍照”会打开实时预览并默认使用后置摄像头；手机和 iPad 可在弹窗中切换前后摄像头，“从相册上传”仍是独立入口。相册照片在 Web Worker 中缩放和编码，相机画布直接生成 JPEG。当前网页固定调用 `verificationPhoto v3`，先用迁移 039 建立／复用数据库上传任务并锁定随机对象，再把 JPEG 和任务绑定证明通过 CloudBase `callFunction` 提交给照片函数；不再依赖浏览器 PG 存储 PUT 签名。每张核销单在数据库层最多只有一个进行中的补充照片任务，必须成功、权威失败或经服务端确认取消后，才允许上传下一张，避免无归属对象、多标签页或慢请求反向覆盖新照片。

静态原型中的删除采用软删除：对象状态改为“已停用”，不删除历史充值、核销、客户或统计引用。
新增和停用操作在当前页面会话中立即生效；刷新页面后恢复示例数据。正式部署时由后端数据库持久化并记录账号、姓名、时间和审计日志。

总部首页使用 `staffAccount` v41 的 `getHqDashboard` 从 PostgreSQL 汇总真实数据，不再使用空数据源、按天比例缩放或虚构的环比百分比。默认范围是上海时区当天及此前29个自然日；自定义范围最多366日。页面只统计当前仍为 `APPROVED` 的工单；充值作废通过后原单成为 `VOIDED` 并从其原提交周期汇总中移除。按门店统计从门店主表完整列出所有门店，所选日期内没有有效业务的门店也显示名称、短编号和数值 0。

门店项目对比图的纵轴显示“次数”，从0开始，并根据当前筛选数据自动采用1、2、5及其10倍数量级的易读刻度。
纵轴上限会随筛选结果动态变化，但同一张图中的充值柱和核销柱始终共用同一纵轴；横向滚动时纵轴固定可见。

时间周期使用自然日历口径：“本年截至今天”为当年1月1日至系统当天；第一季度为1—3月、第二季度为4—6月、
第三季度为7—9月、第四季度为10—12月。已结束季度统计完整季度，当前季度截止到今天，尚未开始的季度显示暂无数据。
另提供“本周（周一至今天）”和“本月（1日至今天）”。所有业绩统计均包含活跃和已存档客户，只按业务记录有效性与所选时间周期汇总；
客户存档或恢复不会追溯改变历史有效充值、核销和业绩。
选择周期后自动填写开始和结束日期；手动修改日期时自动切换为自定义周期。

全局视图是默认首页，只提供时间周期、开始日期和结束日期调整，并固定显示按门店、按项目和按老师三张图。
三张全局统计图采用一图一行的纵向布局：门店统计一行、项目统计一行、老师统计一行；每张图内部继续支持横向滚动。每个分类对象在横轴完整显示名称和短编号，充值／核销的每根柱直接标出数值，不再用省略号截断对象名称。
全局视图不显示“充值与核销趋势”图，也不生成任何合成趋势。门店、项目、老师和分类方式不放在全局首页；
具体对象及逐笔业务通过管理、客户查询、充值查询和核销查询页面查看。
全局“完整排名”表右上角提供分类维度下拉框，可以在门店、老师和项目之间切换并立即重新计算排名与占比；
老师维度只统计有效核销次数，有效充值列显示为“—”。

`local.html` 现在是运营账号的本人首页：个人资料通过 `staffAccount/session` 从数据库读取，页面只提供充值审核和核销审核入口，不展示门店、客户、产品或业务统计。运营没有客户建立、办卡充值、核销办理或补录核销入口，也不能直接调用这些办理动作；其客户与工单详情访问仍必须来自真实审核上下文且保持只读。

老师账号的首页是 `teacher-work-orders.html`。页面只从数据库读取当前登录老师的基础信息，以及 `teacher_id` 确实绑定到本人的充值和核销工单；客户姓名与编号只显示为工单上下文，不生成客户主页链接。老师没有客户建立、客户查询、客户主页、客户照片管理、总部审核或任何管理页面权限。老师仅可办理充值、正常核销和补录核销，且必须先选择本次办理的唯一活跃门店，随后复用门店的客户确认、项目余额和 1:1 人脸核验流程；服务端始终把工单老师锁定为当前登录老师，浏览器不能替换为其他老师。补录核销必须填写原因并进入审核队列，不会直接消耗次数或发送设备开启信号。

部署为网页时：

1. 按编号依次执行尚未运行的数据库迁移；正式 migration 工具使用完整的 `037_verification_photo_evidence.sql` 与 `038_verification_profile_photo_snapshot.sql`，腾讯云 `ExecutePGSql` 控制台必须改用 `database/cloudbase-console/` 下的七个短文件并严格按 `037-01` 至 `037-03`、`038-01` 至 `038-04` 执行；若 `037-01` 已成功而旧版 `037-02` 报 `SQLSTATE 42601`，不要重跑 `037-01`，先单独执行 `ROLLBACK;`，再从当前 `037-02` 继续；
2. 执行迁移 `039_direct_verification_photo_upload.sql`（CloudBase SQL 编辑器应依次执行独立的 `039-01` 至 `039-05`），建立短时上传任务、每单唯一进行中任务和原子提交函数；
3. 可选在 CloudBase PG 云存储中新建私有桶 `verification-photos`；也可以把 `VERIFICATION_PHOTO_BUCKET_ID` 和 `CUSTOMER_PHOTO_BUCKET_ID` 都设为现有私有桶 `customer-photos`。两个云函数会对候选桶去重并查询当前 PostgreSQL 环境的真实 `storage.buckets.id`，候选桶都不存在时直接拒绝。`faceRecognition` 与 `verificationPhoto` 的环境变量必须在各自函数中分开配置，并在 CloudBase 控制台“一项变量一行／一个输入框”；不能把整段 `KEY=value` 文本粘到任意单个变量值中。两边优先使用平台托管的 `CLOUDBASE_APIKEY`，仍兼容旧 `CLOUDBASE_SERVICE_ROLE_KEY`，并配置同一个至少 32 位安全随机 `VERIFICATION_PHOTO_CLEANUP_TOKEN`。清理凭证只用于无终端用户 UID 的控制台手工补跑，绝不能写入 Timer JSON。`CUSTOMER_PHOTO_URL_TTL_SECONDS`、`VERIFICATION_FACE_EVIDENCE_TTL_MINUTES` 及全部 `FACE_*` 只配置在 `faceRecognition`。在现有云函数安全规则中合并 `verificationPhoto.invoke = auth.loginType != 'ANONYMOUS' && auth != null`，同时保留必需的顶层 `*` 和所有其他函数条目；客户端出现 `EXCEED_AUTHORITY` 时检查该项、登录类型和会话。平台 Timer 不走普通客户端 `invoke` 授权。两个函数分别保存 triggers-only 定时配置：`faceRecognition` 使用 `cleanup-verification-photo-drafts-hourly`，`verificationPhoto` 使用 `cleanup-verification-photo-uploads-hourly`；触发器不携带业务 `action` 或凭证。静态站点域名须加入 Web 安全域名；当前补充照片通过云函数传输，不要求桶开放浏览器 `PUT` CORS；
4. 部署 `staffAccount-v41.zip` 与 `faceRecognition-v55.zip`，调用各自 `health` 核对版本，并先验证原有建档、活体、1:1 核销人脸，以及总部必须选择唯一 `ACTIVE` 门店后才能使用四个共享办理入口；
5. 新建或更新名称精确为 `verificationPhoto` 的云函数，部署 `verificationPhoto-v3.zip`，配置同环境的服务端 Key 和照片桶、512 MB 内存、60 秒超时，再调用 `health` 确认 `version: "v3"`、`ready: true`、`verificationPhotoUploadSchemaReady: true`、桶和服务端存储均就绪。该函数固定通过 `FUNCTION` 模式接收补充照片，同时重新核验真实对象大小、MIME、JPEG 内容、尺寸和 SHA-256；原图与导出继续按同一账号、工单和照片位权限通过鉴权存储通道读取；
6. 部署当前静态文件到 CloudBase 静态网站托管并强制刷新浏览器；
7. 通过总部、运营、门店和老师真实账号完成角色边界回归，并验证总部四个办理入口只能选一个活跃门店、无“全部门店”；同时完成核销照片查看、总部／门店／老师原提交人上传或替换、取消后重试、非提交人拒绝和 24 小时截止测试。

如果生产库已经成功执行迁移 039，本次 v55／v3 更新没有新增 SQL 或 migration，不要重跑 037--039；只需按“`faceRecognition v55` → `faceRecognition health` 与人脸／总部办理冒烟测试 → `verificationPhoto v3` → `verificationPhoto health` → 配置两个 Timer → 当前静态前端 → 强制刷新浏览器”的顺序更新。不要在旧 v54／v2 上先启用新 triggers-only Timer，旧函数会把 Timer 当成 `health` 而不会清理；也不要先发布新前端，否则旧函数会拒绝总部办理或照片动作。部署前在同一 CloudBase 环境的 PostgreSQL SQL 编辑器执行 `SELECT id FROM storage.buckets WHERE id IN ('customer-photos') ORDER BY id;`，当前两个桶环境变量都为 `customer-photos` 时应恰好返回这一行；同时用 `SELECT TO_REGCLASS('public.verification_photo_upload_requests');` 确认迁移 039 表存在。完整配置、触发器和健康检查预期见 `cloudfunctions/verificationPhoto/README.md` 与 `cloudfunctions/faceRecognition/README.md`。

核销详情的高清原图查看器支持按钮、鼠标滚轮、键盘、拖动和手机／iPad 双指缩放。页面先显示缩略图，高清图解码完成后再替换；临时签名地址不可用时，查看器会在相同工单权限和查看审计下改用 `verificationPhoto` 的鉴权读取通道取回原图，并且只创建当前页面内存 Blob，不持久化照片。最多只保留两张已解码原图，减少连续查看照片造成的内存占用。

生产环境不得信任前端传入的门店或账号权限范围，所有数据权限必须由后端根据登录账号重新校验。
