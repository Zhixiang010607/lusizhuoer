## 跨设备项目规则

客户人脸、充值、退费、正常／体验核销、业务归属、照片、统计、P0 防重、移动端、

## 客户端边界与交付

- 仓库根目录现有 HTML、CSS、JavaScript 是网页版兼容边界；微信小程序代码只在 `miniprogram-app/`；未来原生 App 代码只允许进入 `native-app/`。
- 各客户端共享 `cloudfunctions/` 和 `database/` 的服务端契约，但不互相导入 UI、路由、会话存储、平台 API、依赖或构建产物。单端修改默认不碰其他端；共享接口变化必须分别回归每一端。
- 云函数代码变化必须提供 `deployments/<函数名>-v<版本>.zip` 的可点击本机链接。需要在腾讯云执行的 SQL 必须是 `database/cloudbase-console/` 下可整文件复制粘贴的独立文件。
- 验证完成的代码必须提交并推送；代码推送、SQL 执行、云函数上传、网站发布和小程序发布仍是五个独立状态，交付时分别说明。
- 页面、按钮、查询和三角色回归的当前覆盖与未提交边界见 [`QA_ACCEPTANCE.md`](QA_ACCEPTANCE.md)。

## 微信小程序

`miniprogram-app/` 是复用当前 CloudBase 后端与同一员工 UID 权限的原生微信小程序。仓库范围包含外壳、手机号密码登录、用户点击授权的微信手机号快捷登录、与网页版手机内容区逐项一致的总部／门店／老师首页、客户／充值／核销数据库查询及精确工单详情、总部项目／产品／门店／老师管理、总部充值／退费／核销审核、客户查询与建立、充值／退费、正常／老师体验核销；BLE 是下一阶段。小程序内部使用暖象牙白、浅香槟金和深咖主题，但继续按网页版手机端复刻布局、按钮、查询和业务逻辑。网页和小程序只统一视觉层级与业务语义，客户端源码、路由、会话和平台能力仍物理隔离。导入、构建、安全与断网防重验收见 [`miniprogram-app/README.md`](miniprogram-app/README.md)。

当前小程序开发基线为 Node.js `>=20.19.0`、pnpm `9.15.9`、CloudBase JS SDK `3.7.1` 和微信开发者工具；依赖必须按 `pnpm-lock.yaml` 冻结安装，不再使用会产生第二份锁文件的 `npm install`。当前开发 AppID 为 `wxb053c1bd6c684d8b`，CloudBase 环境授权已经成功，仍需在微信公众平台为该 AppID 配置 CloudBase `request` 合法域名。AppID 可公开但任何密钥都不得写入仓库。现有 CloudBase 是 PostgreSQL 环境，不走微信开发者工具的“云环境转换”；小程序通过 SDK 与微信适配器复用同一环境和云函数。

> 当前代码版本矩阵为 `staffAccount v75`、`faceRecognition v95`、`verificationPhoto v9`、`teacherCreate v6`。产品主档、充值赠品和独立产品购买必须依次执行并验收迁移 060、061、062，再人工上传 `deployments/staffAccount-v75.zip` 与 `deployments/faceRecognition-v95.zip`。本版新增门店／老师顶部“办 → 产品购买”、总部独立“产品购买审核”、客户主页“产品名称／购买／赠送”三列汇总，以及底部业务记录第五项“产品”；购买不做人脸、不进入项目次数或库存，只有总部审核通过才累计。代码推送、SQL、云函数、网页发布、小程序开发版上传、设为体验版、提交审核和正式发布仍分别计算。

## 腾讯云客户人脸识别后端

`cloudfunctions/faceRecognition/` 是 CloudBase 人脸与业务云函数源码。它使用腾讯云人脸识别的人员库与 1:1 核验能力，人员库 ID 为 `lusizhuoerdatabase`；客户首次授权建档时录入人脸，后续核销只与已经选定客户的档案核验。`cloudfunctions/verificationPhoto/` 是独立核销照片云函数，不安装腾讯人脸 SDK，只处理照片查看、导出和三个补充照片位的上传／取消／恢复。函数密钥只能配置在 CloudBase 环境变量 `FACE_SECRET_ID`、`FACE_SECRET_KEY` 中，严禁出现在网页代码、GitHub 或文档中；照片函数不需要这两个变量。

前端通过已登录 CloudBase UID 调用云函数，门店、总部及客户范围均在服务端重新校验。正式处理真实人脸数据前仍必须确认活体检测服务、客户明确授权、人脸数据删除渠道和访问审计均已启用。

## 员工登录与账号唯一性

- 一个中国大陆手机号只能绑定一个业务身份；手机号码全局唯一，已绑定后不可再次注册或改绑给其他总部、门店或老师身份。
- 账号创建仅由已授权总部在网页端发起；后端同时创建身份认证用户与业务档案绑定记录。未预先绑定的手机号不能通过短信自助注册进入系统。
- 员工可使用“手机号 + 密码”、“手机号 + 短信验证码”或微信小程序手机号授权登录；三种方式必须关联到同一既有 CloudBase Auth 用户和同一 UID，不产生第二个账号。
- 微信手机号授权只能由用户点击按钮发起。授权后由 CloudBase 验证微信一次性 code 并匹配已有 Auth 用户；客户端输入或传入的手机号不是身份证明。
- `session` 只按当前已验证 CloudBase UID 回读员工角色、状态和门店范围。禁止用手机号自动替换 `auth_uid`，禁止陌生手机号自动注册 Auth 或业务账号；UID 未命中时必须失败并退出会话。
- 修改密码须由当前已登录用户完成短信二次验证；总部可发起重置，系统记录操作人、时间和原因。初始 12 位密码仅作首次/应急登录凭据。

### 微信手机号快捷登录前置

- 在同一 CloudBase 环境启用 `WX_MICRO_APP` 身份源，配置当前小程序 AppID 和只由 CloudBase 服务端保存的 AppSecret。
- 显式配置 `On=TRUE`、`AutoSignInWhenPhoneNumberMatch=TRUE`、`AutoSignUpWithProviderUser=FALSE`、`TransparentMode=FALSE`、`ReuseUserId=FALSE`；保留手机号＋密码登录，不得依赖控制台默认值。
- 微信小程序必须为已完成认证的非个人主体，并在发布前完成手机号用途的用户隐私保护指引、接口声明和页面授权文案。
- 按微信和 CloudBase 当期政策开通小程序手机号验证能力及所需套餐／计费，并使用真机验证授权、拒绝、未绑定员工和封存员工场景。

## 总部基础资料创建规则

- 门店创建为独立页面；填写门店名称、完整地址，并可添加多组联系人姓名与电话。提交后自动生成门店编号、门店账号与12位数字初始密码。
- 新建老师只填写姓名、联系电话和初始密码；独立 `teacherCreate v6` 云函数在一个同步请求内创建 ACTIVE 登录账号与 ACTIVE 老师主档并回读确认。老师不上传照片、不建立人脸，人脸不是创建、激活、登录或业务选择条件。手机号是唯一外部身份，一个手机号只能对应总部、门店或老师中的一种身份。老师管理支持按姓名或联系电话查询；管理页只支持封存，不提供删除操作。
- 老师体验额度与客户项目余额完全独立：总部在每位老师的详情内按活跃项目设置唯一的月度基础额度，并可为该老师的指定项目单独充值。每次配置立即以新次数覆盖当前可用额度；删除配置只封存当前额度，随后可重新配置，历史配置、重置、充值和体验消耗均保留。每月上海时间 1 日 00:00 仅重置活跃老师、活跃项目和活跃配置。体验核销只会原子扣减老师项目的可用体验次数，绝不扣减客户剩余次数，并显示各项目全历史体验总数。
- 总部侧栏不再设置“创建”菜单；门店、项目、产品与老师均只能从各自管理页的“新增”按钮进入创建页。
- 门店管理首次进入仅提供“门店名称＋省/州＋城市＋区”选择和新增门店；确认选择前不显示门店资料。确认后展示门店信息、统计和“查看门店页面”入口；同名门店自动以 `1`、`2`、`3` 区分。
- 示例门店统一使用中国省、市、区；新建门店时省、市、区为联动下拉选择。完整三级行政区划数据保存在本地 `china-regions.js`，离线打开原型时同样可用。
- 门店管理还支持手动输入门店名称并依次选择省、市、区；系统先弹出详细地址和联系人方式供核对，确认无误后才跳转至门店页面。
- 项目管理一次展示全部项目；点击某个项目进入项目单据模板。独立产品管理使用“产品列表 → 独立产品创建”流程，创建页只填写产品名称；数据库保存自动生成的产品编号、名称和活跃／封存状态，不提供模板、配置或删除。
- 正常和体验核销均须完成客户人脸识别、现场照片证据与活体／1:1 比对；正常核销只会扣客户余额，体验核销只会扣所选老师的体验次数，二者均在通过后发送设备开启信号。
- 充值不需要人脸识别，也不采集刷脸或拍照凭证。固定按“确认客户 → 填写充值信息 → 填写产品赠予”办理；第三步可为空，也可以按“选择激活产品 → 填写数量 → 点＋加入”的顺序加入最多 20 种赠品，提交前逐条删除。退费不能附带赠品。
- 门店、老师和总部账号密码仅总部可在对应管理页面查看或修改；静态原型中密码仅保存在当前浏览器会话，正式部署须改由后端保存密码哈希并记录审计日志。

直接双击 `login.html` 或运行 `open-dashboard.cmd` 即可离线打开统一登录入口，不需要安装依赖或启动服务器。
登录页只提供总部、门店和老师三种身份；门店登录必须选择所属门店。静态版接受任意非空密码，
只在当前标签页的会话存储中保存单一演示会话，不保存密码；重新选择身份登录时先清除上一身份会话，避免角色状态混用。
总部进入数据库全局工作区；门店直接进入所选门店工作区，老师进入个人工作台。未登录访问业务页面、直接输入其他身份页面地址、
或者门店修改URL中的门店编号时，`auth-ui.js` 都会拦截并返回本身份首页。侧栏只生成当前身份允许的入口，并提供账号、门店及退出登录。
总部的客户、充值和核销查询使用同一套数据库页面，可查看全部门店或选择一个具体门店；门店账号的三类查询固定锁定到登录门店，不能选择“全部门店”或其他门店。页面选项只决定筛选条件，最终权限仍由云函数根据 CloudBase UID 校验。
前端路由隔离不是安全边界：`staffAccount`、`faceRecognition` 和 PostgreSQL RLS 都会再次按 CloudBase UID、账号状态和角色校验。历史运营账号会被封存并拒绝会话、审核、客户资料和照片读取；其既有审核记录继续保留作审计。

业务办理只允许门店和老师账号。总部侧栏不显示客户建立、办卡充值、退费申请或核销办理入口，旧页面地址也会被前端权限表送回总部首页；云函数对总部账号的直接调用统一返回 `FORBIDDEN`。门店账号由服务端 UID 锁定到登录门店；老师办理前必须选择一个真实、活跃的门店，老师身份始终由登录账号锁定。

- `customer-create.html`：客户建立，必填姓名、生日，强制现场拍摄建档照片，保留面容录入、活体/质量检查与授权逻辑，并填写特别注意事项；
- `recharge-create.html`：办卡充值，可选择现有客户并自动带出只读生日，或手动输入姓名和生日；只匹配已确认门店的活跃客户，确认后选择项目、次数和可选业务老师，再从独立产品主档选择激活产品与数量加入赠品清单；充值不做人脸识别；
- `verification-create.html`：核销办理，沿用已确认门店的活跃客户检索，选择项目和老师，人脸核验及现场照片绑定成功后才允许正常核销并发送设备开启信号；
- 补录核销入口已经移除；当前只保留正常核销，以及老师本人可发起的体验核销。

门店和老师的共享办理页面复用相同 DOM、校验、提交和返回链；每个云函数请求都会再次按当前 UID、角色和目标门店状态校验，不能依赖前端缓存扩大范围。总部仍可在查询页使用“全部门店”筛选、处理审核并查看已有业务详情，但不能新建任何客户或业务工单。

`store-business.js v0.14.60` 在调用云函数前先把不含明文客户资料、留言或人脸令牌的请求指纹与 `clientRequestId` 写入浏览器并回读确认。调用超时或断网后只允许用同一编号查询原工单；数据库尚未给出确定结果时页面保持锁定，不会重新生成编号、重复充值或再次扣次。云函数已确认成功后，请求锁一直保留到对应详情页真实加载并确认同一编号后才清除。

办卡充值和核销办理的客户区提供两种检索模式：“现有客户下拉框＋生日”以及“手动输入姓名＋生日”。现有客户模式选择带编号的客户后，生日由客户主档自动带出并保持只读，不能在查找流程中修改；只有手动模式允许选择生日。查询后左半栏显示
客户建档时拍摄的当前有效照片、姓名、生日和客户编号，不再显示各项目剩余次数；必须点击“确认此客户”后右半栏才解锁。建档照片不存在或读取失败时不得确认客户。办理页的现有客户使用下拉框，不直接铺开客户列表；下拉框启用前按稳定游标自动读完该门店全部活跃客户，每批最多 100 位，点开后可上下滑动选择全部客户。姓名＋生日仍作为并行精确查询方式，而不是第 101 位以后客户的唯一入口。切换门店或查找模式会使旧请求失效，照片短时地址只在当前授权范围内复用。核销人脸原图优先保留到最长边 1920 px、JPEG 0.92，并另存 480 px 缩略图；只有超过 3 MB 才逐级缩小。
切换方式或修改条件会撤销确认并重新锁定。
正常核销项目下拉框只加载客户剩余次数大于零的项目；体验核销则只加载所选老师已配置、当前活跃且体验次数大于零的项目，并直接显示老师可用次数。

静态原型只保存当前标签页中的演示状态，不采集真实面容或照片。正式部署时，客户和门店范围必须由服务端会话确定，
面容录入必须使用受控摄像头、活体检测、质量检查、加密模板和授权审计，不能由前端自行声明成功。
客户建立、办卡充值和核销办理页面在桌面端使用尽量占满可用工作区的拉伸布局；充值和核销采用左右双栏，
左侧持续显示客户检索结果，右侧完整显示项目、次数、采集状态和提交结果，窄屏时自动切换为单栏。

项目栏中的“管理”可以展开四个子页面：

- `store-management.html`：新增、选择和查看门店；列表不直接修改状态，只有总部进入门店主页后才能封存或激活门店；
- `project-management.html`：新增、查看、封存和激活项目；项目进入独立单据模板页，用户文案不再使用“产品”；
- `retail-product-management.html`：涂抹类／实物产品列表，只提供“新增产品”入口以及封存／重新激活操作，不能删除；
- `retail-product-create.html`：独立产品创建页，只填写产品名称，保存后由数据库自动生成 `PDT...` 编号并返回产品列表；
- `teacher-management.html`：新增、选择、查看和删除/停用老师；查看老师在各门店、各项目的核销统计。

老师账号的首页是 `teacher-work-orders.html`。手机版基础资料只显示老师姓名和老师短编号，同一横排等宽展示，不重复登录身份；每个体验项目按“项目、可用、每月基础、本月已用”占一条紧凑横排。总部进入老师主页后的档案、账号与体验额度管理直接使用其他内部页面同款的暖象牙白卡片、浅象牙内层和细金灰边框，深咖底色只保留给共用顶部栏及少量主按钮，不再混用多块深色或不同色相背景；业务区支持今天、本周、本月、本季度、本年、全部和自定义日期，默认今天。所选周期生成“产品为行、四类业务为列”的有效次数汇总矩阵，并控制后续分页明细。老师业务统计、客户关系和历史业务老师显示均以经服务端验证后写入工单的 `teacher_id` 为准；门店明确选择该老师提交的有效充值、退费或正常核销也计入该老师。历史读取还会校验原提交来源与业务类型：门店来源仅接受充值、退费、正常核销，老师来源仅接受提交账号本人办理的充值、退费、正常核销、体验核销；总部、已退役角色、老师错绑、门店体验和历史补录工单保留业务总量及审计记录，但老师维度按“未指定”处理，不凭该旧字段授予关系或照片读取权。允许留空且未选老师的门店充值／退费不归属任何老师。真实 `submitted_by_account_id` 始终保留原提交人，并继续唯一决定修改、补照片、作废、撤销和防重恢复等写权限；被门店选中的老师只获得统计归属和规定的客户及工单只读权。老师的活跃／封存客户列表与客户主页使用同一关系口径：本人账号创建，或本人 `teacher_id` 已存在任一已通过的正常核销、体验核销、充值或退费。获权后可只读该客户全部历史，但不得改动其他提交人的工单。老师主页只保留业务入口；进入客户建档、充值／退费、普通核销或体验核销具体页面后，第一步重新读取并选择活跃门店，选定后才读取该门店客户并启用后续表单。老师账号的四类业务均由服务端锁定本人。体验核销入口只对老师开放，只验证所选客户的 1:1 人脸，并原子扣减老师体验额度；门店和总部既没有入口，服务端也拒绝绕过。
