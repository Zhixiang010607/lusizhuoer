## 原因

设备历史日志显示，一次 `info` 响应可能约 3.5 秒后才发出；0.2.86 在 2 秒时已补发第二条 `get_info`，因此首条请求仍在设备处理时又进入一条相同请求，随后产生两份逐字相同的 `info`。这不是 signature 或 nonce 算法造成的。

LASER-BLE 当前使用 HC-08 FFE1 的 `writeNoResponse`。BLE Write Command 本身没有远端处理回执，微信写接口成功只表示本机蓝牙栈接受了写入；完整业务响应仍必须由 `info`、`auth_result` 或 `status` 确认。因此固定增加 50ms、100ms 或 1 秒不能从协议上保证可靠。

## 修复

- `get_info` 只建立一个 10 秒等待器；首条发出 5 秒且完全没有收到任何通知字节时，才补发一次字节完全相同的请求。
- 已经收到任意设备分片时，不再补发，只继续组装完整 JSON。
- `auth` 绝不自动重发；缺少 `auth_result` 时只发送 `query_status` 查询真实工作状态。
- 关闭或取消扫码后，旧通知监听、连接和蓝牙适配器按完成回调依次关闭；旧会话回包直接忽略，新会话使用全新缓冲区。
- 服务端授权开始前可以关闭并在剩余 90 秒资格内重扫；授权已经开始或发出后禁止普通重扫，必须恢复原设备状态，避免重复启动。

设备端应保证：一条完整请求只发送一条响应；完全相同的 `cmd + seq + ts` 只重发缓存的 `info`，不改变状态；重复 `auth` 不得再次启动，只返回当前真实状态。
